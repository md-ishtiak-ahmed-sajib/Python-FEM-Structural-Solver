# Keep pages clear, linked and up to date

[Project home](../../README.md) · [Documentation map](../README.md) · [Section guide](README.md)


This guide helps contributors maintain the documentation for BSc civil engineering students.

## Put each page in the right place

| Section | Purpose |
|---|---|
| 01 Project vision | Why the project exists, its requirements and limits |
| 02 Getting started | Installation, first calculation and repository map |
| 03 Engineering knowledge | Concepts, equations, units, glossary and learning |
| 04 User guide | App steps, Python functions, file formats and errors |
| 05 Research and experiments | Research question, synthetic protocol, bench work and report |
| 06 Software design | Code structure, interface rules and design decisions |
| 07 Testing and evidence | Check methods and the limits of current evidence |
| 08 Contributing and release | Ways to help, attribution and publication |
| 09 Project records | Milestones, current state and documentation rules |

Use lowercase filenames with hyphens. Numbers sort the topic folders in a useful reading order. Do not create several pages that claim to be the current status.

## Write for a student

Start by saying what the page helps the reader understand or do. Use short sentences and familiar verbs. Explain technical words on first use and link to the glossary.

Keep established equations, units, function names and file keys correct. Simple English must not remove a scientific limitation.

Use a small worked example when it helps. Distinguish an example input from a recommended physical test load.

## Connect every page

Every page needs a link to the root README. Topic pages also link to their section guide and to useful related pages.

Add every documentation page to the complete index in the root README and to the appropriate section README. The docs README helps readers choose a route.

Use relative links so navigation works in GitHub and in the downloaded source. Link figures to their actual files. Do not add a private absolute PC path.

## Diagrams and tables

Use tables for comparisons. A small Mermaid diagram can show the calculation or reading path. Add a plain-text explanation for editors that do not render it.

Do not use a diagram as evidence of an experiment. Keep units, signs, data origin and limitations visible on scientific figures.

## Generated documents

The research report is generated by scripts/reproduce_artifacts.py. Edit its template in that script, then regenerate the report. Editing only the output would lose the change next time.

The glossary is generated from src/fem_solver/terms.py with scripts/build_learning_docs.py. That script also creates the original element-family SVG and PNG figures. The app and glossary must use the same reviewed definitions. Run the script with --check to detect drift.

The README's convergence graph must identify the uncorrected cubic Hermite field. Do not relabel it as convergence of the already corrected exported displacement field.

Study and check records contain fixed machine-readable keys. Explain unfamiliar keys in the user guide or glossary rather than silently changing the file format.

## Check before finishing

Run python scripts/check_docs.py. It checks local links, home links, the root index and section navigation.

For code or app wording changes, run the relevant software checks too. Keep [milestones](milestones.md), [working memory](working-memory.md) and the root changelog factual.

Do not rewrite the legal license into informal English. Explain it separately and preserve its terms.
